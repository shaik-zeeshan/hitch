# Remote Daemons are reached through an SSH stdio proxy

Hitch remote support connects the GUI to a long-lived Hitch **Daemon** running on the SSH host, not to a local-daemon-owned remote shell. The GUI starts `ssh <host> hitch daemon proxy`; that remote proxy auto-starts or attaches to the host-local daemon endpoint and bridges the existing Hitch protocol over SSH stdio. This keeps Sessions, Jobs, git operations, Worktrees, and Agent State owned by the daemon on the machine where the work happens, while avoiding a daemon network listener or cross-platform socket forwarding.

## Considered Options

- **SSH stdio proxy** — chosen because SSH already supplies authentication/encryption, no port is exposed, and remote agent hooks keep using the remote daemon's local socket/pipe.
- **SSH port/socket forwarding** — rejected because Unix-socket and Windows named-pipe forwarding would make the transport model platform-shaped at the GUI boundary.
- **Remote TCP listener** — rejected because it creates a new security surface and auth model outside Hitch's current local-endpoint daemon design.
- **Manual remote daemon endpoint** — rejected because it makes remote setup brittle and leaves users responsible for daemon lifecycle.

## Consequences

An **SSH Host** is GUI-local attachment configuration and stores only an OpenSSH target string (`prod`, `user@example.com`, etc.); it is not stored in the local daemon's Project registry or in any remote daemon. Hitch shells out to `ssh -o BatchMode=yes` and relies on the user's OpenSSH config, ssh-agent, hardware keys, ProxyJump, and known_hosts; it does not store private keys or passphrases, and it does not allow host-key/password/passphrase prompts on the protocol stream. The remote host must have a compatible Hitch daemon/proxy binary preinstalled and available as `hitch`; the GUI validates version compatibility and reports an install command when it is missing or stale. Hitch deliberately does not auto-upload remote binaries in the first design, keeping the trust boundary explicit. The proxy is connection-scoped, but the daemon it attaches to remains detached and survives GUI disconnects, preserving the existing daemon-owned session model.

The Add SSH Host dialog has one required field: the OpenSSH target. It offers Test Connection before Save; the test runs the same non-interactive SSH/proxy/version path and surfaces classified actionable failures for auth/agent, host-key trust, missing `hitch`, protocol mismatch, proxy startup, and network/VPN. Errors include the exact manual test command: `ssh -o BatchMode=yes <target> hitch daemon proxy`.

Remote SSH Hosts are in scope for every daemon-supported OS, including Unix and Windows. The SSH stdio proxy hides whether the remote daemon's host-local endpoint is a Unix socket, Windows named pipe, or another local transport; platform-specific path/PTy/process behavior remains inside the remote daemon.

The GUI presents local and remote daemon registries together in a single flat multi-daemon tree: there are no top-level Local/SSH-Host scope parent rows. Projects from every attached daemon hang directly off the tree root, ordered Local first then each host's Projects grouped together with hosts sorted alphabetically by target string. The owning daemon scope is still authoritative — Project, Worktree, Session, and Job identifiers are interpreted within their owning daemon scope, never as globally unique across all attached daemons — it is only no longer a visible parent row. A Remote Project carries its scope inline on the Project row as a quiet cloud glyph plus the dim OpenSSH target string (`user@example.com`), immediately right of the Project name; Local Projects render no such badge and look unchanged.

With the host parent row gone, the host's Daemon Status and the same derived Agent State rollup used for Projects/Worktrees ride the Remote Project rows themselves (a stale host greys its Projects' rows as stale UI), and the per-host actions move onto the Remote Project context menu: Remove host is always available, and Retry Now appears there while the host is unreachable/failed. Both are GUI-local affordances, so they stay enabled while the host's daemon-backed actions are disabled. Adding a Project to a host is no longer a host-row action; it lives on the global add control in the left rail.

Agent State from every connected daemon participates in the same global attention surfaces as local Agent State; labels and navigation include the local/SSH Host scope so a remote approval is attributable.

Session tabs stay scoped to the active Project/Worktree parent, as today; remote support does not put Sessions from different daemon scopes into one tab strip. While a remote parent is selected, host context is carried by the selected tree row rather than repeated in tab titles or a new center breadcrumb.

Global search surfaces such as the command palette include the local/SSH Host scope as muted metadata (`prod · project · branch`) for remote Projects/Sessions, without changing Session tab labels.

Global actions operate on the currently selected daemon scope, or on the owning daemon of the selected Project/Worktree/Session. Dialogs show that target scope and may let the user change it, rather than duplicating command-palette actions per host.

Remote destructive confirmations always include the SSH Host name and remote path (for example, `Remove worktree on prod?`) so a path that also exists locally cannot be mistaken for local state.

Saved SSH Hosts are enabled by default: the GUI connects to every saved host on launch and auto-reconnects when the SSH/proxy connection drops. Reconnect uses a short exponential backoff (~2s, 5s, 15s, 30s, then capped around 60s with jitter). The remote Daemon and its Sessions continue running; the GUI marks the host unreachable, keeps that host's last Project rows greyed as stale UI, disables daemon-backed actions in that scope, and replaces them from daemon replay after reconnect. A Retry Now action (on the Remote Project context menu, surfaced only while the host is unreachable/failed) resets backoff after the user fixes VPN, ssh-agent, or host setup.

Removing an SSH Host forgets only the GUI-local host entry and disconnects the proxy; it does not shut down the remote Daemon or kill remote Sessions.

Adding a Project inside an SSH Host scope uses a remote directory browser backed by daemon requests on that host, then sends the existing AddProject/CloneProject operations to that remote daemon. The browser opens at the remote daemon user's home directory, can navigate anywhere that user can read, and allows typing an absolute path. The UI is a folders-first list with a path bar, parent/home controls, hidden-folder toggle defaulting off, and explicit loading/error rows. The GUI never maps remote paths onto local paths.

Dropping local files onto a remote Session uploads them over the existing Hitch protocol stream to the remote Daemon, which writes them to a per-session remote directory under `~/.hitch/uploads/<session-id>/` and then inserts the uploaded remote paths into the shell. This preserves the local terminal drop behavior without pretending local paths exist remotely, avoids a second `scp`/SFTP connection, and works through the same SSH stdio proxy on Unix and Windows remotes. The remote Daemon owns upload cleanup and deletes that per-session directory when the Session closes.

Remote file-drop upload supports regular files only in the first design. It shows progress, allows cancellation before paths are inserted, rejects directories with explicit copy explaining that recursive upload is not supported yet, and auto-suffixes filename collisions inside the per-session upload dir (`file.txt`, `file-1.txt`, …) before inserting the actual remote paths.

## Amendment (2026-06-08): local `hitch` CLI self-install (Approach C — path from the Hello)

The **goal** of self-install is narrower and more honest than first stated: the **Hitch client** reaches a **self-installed** host with **zero config**, and a **manual** host just needs `hitch` on its own PATH. Making bare `ssh <host> hitch` work for a *human* against a *self-installed* host is **consciously out of scope** — that would require editing the user's shell PATH (or a registry/sudo step), and the product path is Hitch-GUI-to-Hitch-daemon, not a person typing `hitch` over SSH. So Hitch no longer writes any PATH block into a user's shell rc files; resolution is carried by the protocol instead.

**Approach C — the client learns the daemon's path from the handshake.** The daemon captures its own absolute executable path (`current_exe()`, taken at startup so a moved binary can't stale it) and reports it in `Response::Hello` (new `exe_path` field; `PROTOCOL_VERSION` bumped to 27). The client caches that path **in memory per connection** — *not* persisted to the localStorage host entry, which stays `{ id, target }` — and on every reconnect launches the daemon binary **directly**: shell-free, PATH-free, identical across OSes.

**First-connect candidate sequence.** With no cached path, the client tries a small ordered probe and keeps the winning Hello's `exe_path`:
1. `~/.local/bin/hitch daemon proxy` — the `~` is passed as a **literal arg** and expanded by the remote login shell (the known Unix self-install location).
2. `hitch daemon proxy` (bare) — manual installs and Windows registry PATH.

It falls through 1→2 on a failure **specific to the program we invoked** — `MissingHitch` or `ProxyStartup` (see the 2026-06-08 follow-up for why `ProxyStartup` was added); host-level failures `Auth`/`HostKey`/`Network` (and the terminal `ProtocolMismatch`, plus `None`) surface immediately, since retrying those on the next candidate just doubles latency. **Self-healing:** a `MissingHitch` from an already-cached path (the remote moved or updated its binary) clears the cache and re-runs the candidate sequence.

**Unix self-install is now pure symlink, zero dotfile edits.** On first launch (best-effort, gated to run at most once and never overwriting a conflict or a later explicit uninstall) — and via an Install/Repair/Uninstall control in the Remote Hosts settings section — Hitch symlinks **both** `~/.local/bin/hitch` → the bundled `hitch-daemon` **and** `~/.local/bin/hitch-hook` → the bundled `hitch-hook`. Both links are symlinks, not copies; the second is required because macOS `current_exe()` keeps the symlink path, so the proxy resolves `hitch-hook` next to `~/.local/bin/hitch` and that adjacency must exist for remote agent hooks to fire. Conflict handling is all-or-nothing across the two links: a foreign (non-ours) file at *either* path is never clobbered and reports a `conflict` (install nothing); uninstall removes only the links that are ours. A **one-time legacy strip** sweeps out any old managed `# >>> hitch cli >>>` … `# <<< hitch cli <<<` block left by the previous version (idempotent, a no-op on clean machines). Hitch never edits a user's shell rc files in long-running app code anymore. Dev builds report `unavailable` because there is no bundled sidecar to link.

**Windows reach-in moves into the installer.** The NSIS/WiX installer copies a `hitch.exe` entrypoint into the install dir and adds that dir to the per-user PATH (HKCU), with automatic cleanup on uninstall. Runtime `cli_install.rs` on Windows is **status-only** (no Install/Uninstall actions); the Settings UI shows status with "managed by the Hitch installer — reinstall to repair".

Two latent bugs are fixed alongside: macOS hook adjacency (the second `hitch-hook` symlink above) and the hook lookup now appends the platform exe suffix, so a `hitch.exe` daemon resolves `hitch-hook.exe`.

This does **not** change the original trust boundary: self-install is **local-only**. Hitch still does NOT auto-upload binaries over the network to a remote daemon — a machine without Hitch installed still requires a documented manual install of a compatible `hitch` on its PATH. The manual install uses the known-location form: symlink (or copy) the bundled binaries so that `hitch` and `hitch-hook` sit on PATH — e.g. `ln -s <bundled-hitch-daemon> ~/.local/bin/hitch` and `ln -s <bundled-hitch-hook> ~/.local/bin/hitch-hook`, or place the bundled binaries on PATH named `hitch` (and `hitch-hook` adjacent). The candidate probe's bare-`hitch` fallback is what makes such a manual host reachable.

## Amendment (2026-06-08): Windows reach + handshake robustness (follow-up to Approach C)

Shipping Approach C against a real Windows remote surfaced three gaps. None change the design above; they harden the candidate probe and the handshake so a Windows host (and any host with a chatty login shell) is reachable.

**OS-aware candidate ordering via a learned OS-hint cache.** The first-connect candidate sequence is now ordered by the remote's learned OS family. The client keeps a per-target cache of the remote OS family in `ssh-os-hints.json`, written beside the daemon's other side files in the Hitch data dir (`hitch_proto::transport::default_data_dir()`) — **not** in the localStorage host entry, which still stays `{ id, target }`. It is a derived performance hint, like the in-memory `exe_path` cache: a missing or wrong hint costs at most one extra fall-through attempt, and every successful `Hello` rewrites it authoritatively from the daemon's own reported `os_family` (so it can't be corrupted by shell banners or a missing `uname`). On a host learned to be `Windows`, `candidate_sequence` tries bare `hitch` **first** (Windows puts `hitch.exe` on the registry PATH and `cmd.exe` can't expand `~`, so the `~/.local/bin/hitch` candidate is doomed there) and keeps the known-location candidate only as a harmless fallback; `Unix` and the no-hint first-ever-connect case keep known-location-then-bare. Hints for targets that are no longer saved are pruned (and the file rewritten) when the host set changes.

**Handshake-noise tolerance.** The remote `Hello` reader now skips a bounded number of leading non-protocol lines — blank lines and non-JSON shell noise such as a MOTD, banner, or `Last login: …` — before the `Hello` frame, up to `MAX_HANDSHAKE_NOISE_LINES` (64) lines, after which it gives up as `Malformed` (and `REMOTE_HANDSHAKE_TIMEOUT` is the ultimate backstop). Without this a chatty login shell makes a perfectly good remote look like a broken proxy on every candidate.

**Fall-through widened to `ProxyStartup`, plus Windows shell-error classification.** Two coordinated changes make a Windows known-location miss recover instead of surfacing as Unreachable:
- `ssh::classify` now maps Windows shell "not found" wording to `MissingHitch` alongside the POSIX signals (`exit 127`, `command not found`, …): it matches `is not recognized` (cmd.exe / PowerShell "is not recognized as an internal or external command / the name of a cmdlet …") and `the system cannot find` (path-not-found).
- `should_fall_through` now falls through on `ProxyStartup` as well as `MissingHitch`. The candidate sequence exists to *locate* a working binary, so a failure specific to the program we invoked should try the next location; a Windows known-location miss whose shell wording isn't classified lands in `ProxyStartup` (ssh ran but produced no/garbage `Hello`), and falling through lets the bare-`hitch` (registry-PATH) candidate — exactly what Test Connection runs — prove itself. Host-level categories (`Auth`/`HostKey`/`Network`), the terminal `ProtocolMismatch` (a real but wrong-version hitch — report it, don't mask it), and `None` still surface immediately.

**Windows installer: PATH-registry fail-safe and daemon-stop-before-file-ops.** The NSIS `cli-reach-in.nsh` reach-in now reads `HKCU\Environment\Path` via a direct `RegQueryValueExW` rather than NSIS `ReadRegStr`: `ReadRegStr` returns `""` for a `REG_EXPAND_SZ` value (the normal PATH type), and a populated PATH read as empty would turn the append into a destructive bare overwrite. A two-stage read (size query, then conditional value read) sets an existence guard so the append is skipped when PATH exists but the read came back empty, preventing silent PATH destruction; the real registry type is captured so a `REG_EXPAND_SZ` PATH is written back as `REG_EXPAND_SZ`. Separately, `NSIS_HOOK_PREINSTALL`/`NSIS_HOOK_PREUNINSTALL` now stop a running daemon (`taskkill /F /T` on `hitch.exe` and `hitch-daemon.exe`, then a short sleep) before file operations, so an upgrade/uninstall over a running daemon doesn't fail trying to overwrite or delete the locked sidecar `.exe` — Tauri's template only closes the GUI app, not the detached daemon.

## Amendment (2026-06-14): forwarded ssh-agent for daemon-run git operations

The remote daemon is persistent and detached: the GUI attaches via `ssh <target> hitch daemon proxy`, but the daemon it connects to was typically already running from an earlier, unrelated launch. Git runs as a subprocess of *that* daemon. Because `SSH_AUTH_SOCK` is set per SSH connection and lives only in the proxy process's environment, the long-lived daemon had a stale or empty one — so a daemon-run `git push`/`pull`/`fetch` could not reach the user's forwarded ssh-agent and would fall back to prompting on the remote, where the user can't and shouldn't answer. This amendment threads the proxy connection's forwarded agent through to the daemon's git subprocess.

**The GUI enables agent forwarding.** When launching the `ssh <target> hitch daemon proxy` connection (and the Add-SSH-Host Test Connection probe, so the test reflects the real connection), the GUI now adds `-o ForwardAgent=yes`, gated on a per-host `forwardAgent` toggle that defaults on. This makes sshd create a forwarded ssh-agent socket on the remote for that connection.

**The proxy forwards its socket path as a one-time prelude.** On connect, the proxy reads its own `SSH_AUTH_SOCK` and, if present, writes a single `ConnEnv` control-message line (newline-JSON) to the daemon endpoint before bridging, then bridges transparently as before. The **pure-bridge invariant is preserved**: the proxy still never parses or rewrites GUI↔daemon frames — it only adds its own prelude. It just passes the socket-path string through, so it works on any remote that has `SSH_AUTH_SOCK` (Linux and macOS).

**The daemon stores the sock and injects it on git.** The daemon stores the forwarded sock path per-connection (on `ClientSink`) when a `ConnEnv` arrives, and also refreshes a `DaemonState` fallback (the latest forwarded sock) so background ops can sign while a session is attached. At git-dispatch time it resolves the sock — this connection's value if present, else the daemon fallback — and injects `SSH_AUTH_SOCK` onto the git subprocess. Network git ops (push/pull/fetch/clone) also **always** set `GIT_SSH_COMMAND="ssh -o BatchMode=yes"` and `GIT_TERMINAL_PROMPT=0`, so anything the forwarded agent can't satisfy (e.g. an untrusted host key) fails fast instead of prompting or hanging invisibly on the remote.

**Lifetime.** The forwarded socket lives exactly as long as the proxy's SSH connection. While a session is attached, both user-initiated and background ops can use it (the per-connection value, or the daemon fallback). After disconnect the socket is gone and background ops fail fast rather than prompt. A local (non-proxy) daemon never receives a `ConnEnv` and behaves exactly as before, inheriting env as it does today.

**Trust boundary.** The daemon sets `SSH_AUTH_SOCK` to a path *declared by the connecting proxy* over its host-local unix socket. This is acceptable because the connection is host-local and same-user: the proxy was spawned by the user's own authenticated SSH session, so the declared path is no more privileged than anything the user could already set in that environment. This does not change the original network trust boundary — Hitch still does not auto-upload binaries or open any network listener.
